### P1-01 设计系统 token 已出现系统性命名漂移，浏览器正在静默丢弃有效样式

**位置（代表性）**：

- [src/styles/design-system.css](C:/work/PG%20Butler/PGB1/src/styles/design-system.css:187)
- [src/styles/design-system.css](C:/work/PG%20Butler/PGB1/src/styles/design-system.css:251)
- [src/styles/design-system.css](C:/work/PG%20Butler/PGB1/src/styles/design-system.css:941)
- [src/components/CreateProjectDialog.vue](C:/work/PG%20Butler/PGB1/src/components/CreateProjectDialog.vue:107)
- [src/views/TaskListPage.vue](C:/work/PG%20Butler/PGB1/src/views/TaskListPage.vue:508)
- [src/views/SettingsPage.vue](C:/work/PG%20Butler/PGB1/src/views/SettingsPage.vue:396)
- [src/components/PdfPreviewSection.vue](C:/work/PG%20Butler/PGB1/src/components/PdfPreviewSection.vue:129)

**问题**：

我对全仓 CSS 变量做了“引用 vs 定义”对账，发现当前活跃代码里至少还有以下未定义 token：

- `--font-weight-heading`
- `--transition-fast`
- `--button-height`
- `--bg-elevated`
- `--border-subtle`
- `--color-blue-500`
- `--color-red-500`
- `--font-size-sm`
- `--glass-border`
- `--space-2`
- `--text-quaternary`
- `--z-overlay`

自动扫描统计显示：

- 未定义 token 至少 12 个
- 活跃引用至少 127 处
- 其中仅 `--font-weight-heading` 就出现了 38 处
- `--transition-fast` 出现了 41 处
- `--button-height` 出现了 13 处

这不是“局部样式不规范”，而是 **DesignSystem 自身已经和消费层发生命名分叉**。更关键的是，问题不只在组件里，连 `design-system.css` 自己也在引用未定义 token：

- `font-weight: var(--font-weight-heading)`  
- `height: var(--button-height)`  
- `background: var(--glass-bg-subtle)`  

**影响**：

- 浏览器不会报错，只会把整条声明当作无效值丢掉。
- 这意味着很多 UI 现在实际上依赖浏览器默认值或其他偶然样式兜底，而不是 DesignSystem 真正生效。
- 直接后果包括：
  - 按钮/标题字重丢失
  - 输入框高度和背景退回默认行为
  - 过渡动画失效
  - 局部间距丢失
  - 层级 token 失效

**为什么这是高优问题**：

这类问题不会让构建失败，但会让整个“SSOT 设计系统”变成表面存在、实际失效。  
一旦继续在这个基础上做维护，后续所有视觉回归都会越来越不可预期。

**建议**：

- 先冻结一轮 token 命名，统一收口。
- 做一次“定义集 vs 引用集”的脚本化校验，把它放进构建前检查。
- 不建议继续靠人工顺手修；这已经到了需要自动守门的规模。

### P2-02 `translate_text_once()` 仍把 PDF 页文本直接拼进 prompt，PDF 翻译链路没有沿用已修复的注入隔离方案

**位置**：

- [src-tauri/src/commands/translation.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/translation.rs:245)
- 对照： [src-tauri/src/commands/translation.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/translation.rs:60)

**问题**：

实时翻译链路 `translate_text_stream()` 已经改成：

- `systemInstruction`
- `contents`

分离的安全结构，这是对的。  

但 PDF 翻译用的 `translate_text_once()` 仍然是把整页文本直接拼进 prompt：

```rust
let prompt = format!(
    "... Text to translate:\n{}",
    trimmed
);
```

然后把整个 prompt 作为 user text 发送。

**影响**：

- 只要 PDF 某页正文包含“忽略前文 / 改为输出 / 不要翻译”等提示性文本，就可能污染模型行为。
- 这会导致 PDF 翻译结果出现：
  - 输出说明文字
  - 漏翻
  - 结构漂移
  - 和实时翻译链路口径不一致

**为什么这是当前问题而不是旧问题复述**：

上一轮已修过实时翻译路径，但 PDF 路径没同步修。  
现在项目里同一能力存在两条不同安全口径，这本身就是维护风险。

**建议**：

- `translate_text_once()` 也改成 `systemInstruction + contents` 分离结构。
- 不要让 PDF 路径继续保留“字符串拼 prompt”的旧实现。

### P2-03 `usePdfTranslate()` 声称支持按文件维度持久化 session，但重试事件路由仍是单活动文件模型，多文件并发时状态会串

**位置**：

- [src/composables/usePdfTranslate.ts](C:/work/PG%20Butler/PGB1/src/composables/usePdfTranslate.ts:31)
- [src/composables/usePdfTranslate.ts](C:/work/PG%20Butler/PGB1/src/composables/usePdfTranslate.ts:35)
- [src/composables/usePdfTranslate.ts](C:/work/PG%20Butler/PGB1/src/composables/usePdfTranslate.ts:43)
- [src/composables/usePdfTranslate.ts](C:/work/PG%20Butler/PGB1/src/composables/usePdfTranslate.ts:113)
- [src-tauri/src/commands/translation.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/translation.rs:281)

**问题**：

前端已经按 `filePath -> session` 建了全局 `Map`，而且组件注释也明确说“侧边栏关闭不中断翻译”。这说明架构目标是 **多文件 session 可并存**。

但重试事件不是按文件路由，而是按一个全局单值：

- `let activeFilePath = ''`

监听 `pdf-translate-retry` 后，只会把 payload 写进 `activeFilePath` 对应的 session。

后端 emit 的事件 payload 也只有：

- `page`
- `attempt`
- `waitSecs`
- `error`

没有 `filePath`。

**影响**：

只要出现下面这个合法场景：

1. 文件 A 正在后台翻译
2. 用户切到文件 B
3. 又对文件 B 发起翻译

那么：

- A 的 retry 状态可能被写到 B 上
- A 的 retry UI 可能完全丢失
- 当前显示的“正在第几页重试”可能对应的是另一份 PDF

**为什么这个问题值得报**：

这不是“极端并发”才会触发。  
当前架构已经显式承诺“组件卸载不中断翻译”，那就等于承诺了 session 可能跨文件并存。既然设计已经允许并发 session，事件路由就不能再用单活动文件模型。

**建议**：

- `pdf-translate-retry` payload 增加 `filePath`
- 前端按 `payload.filePath` 命中 session
- 删除 `activeFilePath` 这种单槽路由

### P2-04 TexturePacker `.tps` 预设文件补丁写入失败仍被吞掉，GUI 可能在未打补丁的状态下继续打开

**位置**：

- [src-tauri/src/commands/conversion.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/conversion.rs:168)
- [src-tauri/src/commands/conversion.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/conversion.rs:178)
- [src-tauri/src/commands/conversion.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/conversion.rs:216)

**问题**：

当前序列帧转换流程会：

1. CLI 生成 `.tps`
2. 读取 `.tps`
3. patch `globalSpriteSettings.scale`
4. 启动 TexturePacker GUI

但关键写回步骤仍是：

```rust
let _ = fs::write(&tps_path, patched);
```

也就是写失败直接吞掉，然后继续打开 GUI。

**影响**：

一旦发生：

- 文件被占用
- 磁盘写失败
- 权限问题
- 路径异常

GUI 仍会继续打开，但打开的是 **未按预期打补丁的 `.tps`**。  
后续流程还会继续解析 `.tps` 中的 scale，并据此整理目录，这会把“配置值、GUI 实际值、整理结果”三者之间的对应关系打乱。

这类问题的危险点不是“报错”，而是 **用户不会知道自己正在用旧预设继续工作**。

**建议**：

- `.tps` patch 写回失败必须立刻返回错误，不能继续启动 GUI。
- 这是典型的“关键状态写回失败后仍继续推进流程”，不应静默放行。

### P3-05 预览视频上传仍可能静默保留旧版本，和“最新版本、不做历史管理”的设计约束不一致

**位置**：

- [src-tauri/src/commands/conversion.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/conversion.rs:888)
- [src-tauri/src/commands/conversion.rs](C:/work/PG%20Butler/PGB1/src-tauri/src/commands/conversion.rs:902)
- [src/composables/usePreviewVideos.ts](C:/work/PG%20Butler/PGB1/src/composables/usePreviewVideos.ts:8)
- [INDEX.md](C:/work/PG%20Butler/PGB1/INDEX.md:193)

**问题**：

设计文档和索引口径已经明确：

- 预览视频只标记最新版本
- 不做历史管理

前端 `usePreviewVideos` 也是按“最后一个版本是最新版本”来组织状态。

但后端上传逻辑在删除同组旧版本时仍然是：

```rust
let _ = fs::remove_file(&path);
```

删除失败被吞掉，然后继续复制新文件。

**影响**：

如果旧版本因为占用/权限失败而删不掉，就会留下：

- nextcloud 中同时存在多份旧版本
- 当前上传流程返回成功
- 前端只按“最新版本”视角展示，看不到“清理失败”这一事实

这会让“latest-only”设计在磁盘层被悄悄破坏。

**建议**：

- 旧版本删除失败至少要记录日志，并让调用方知道本次是“上传成功但清理失败”。
- 如果设计坚持 latest-only，那更稳妥的做法是把删除失败当成命令失败返回，而不是静默继续。

这类问题有一个共同点：

这轮最值得重视的不是某一个颜色写死，而是 **“设计 token 定义集”和“消费集”已经分叉**。  
这意味着仅靠 Code Review 肉眼看样式，已经不足以守住 SSOT。

建议把以下检查脚本化：

- 未定义 CSS 变量引用检查
- 版本号多文件同步检查
- 静默 `catch {}` 扫描
- Rust `let _ = fs::write/remove_file/rename` 等关键操作扫描

### 7.3 第一轮修复已经见效，但第二轮开始要转向“收尾型工程治理”

本轮能看到明显进步：

- 事件泄漏被修了

所以当前阶段不建议再做大面积推翻式重构。  
更合理的路线是：

- 先用几轮小而准的修复把剩余维护债清干净

## 9. 建议的处理顺序

### 第一优先级

1. 修复未定义 design token，恢复 DesignSystem 的单一事实来源。
2. 统一 `translate_text_once()` 与 `translate_text_stream()` 的安全口径。

### 第二优先级

1. 修复 `usePdfTranslate()` 的多文件 retry 事件路由。
2. 收口 `.tps` patch 写回失败的静默继续问题。

### 第三优先级

1. 收口预览视频旧版本清理失败的静默路径。
2. 批量清理残留的前端 `catch {}`。

## 10. 本轮结论

PGB1 当前基线已经比首轮审查时健康很多，说明项目具备良好的修复响应能力。  
但本轮也很明确地暴露出一个新阶段特征：

不是“功能对不对”，而是“系统约束有没有继续被认真执行”。

本轮我最建议优先处理的三件事是：

1. 把 design token 漂移一次性收口
2. 把 PDF 翻译链路的两套实现口径统一
3. 把剩余静默失败点从“隐藏问题”改成“可观测问题”

如果这三件事能收干净，项目的维护稳定性会再上一个台阶。

### P1-01 保存考勤设置会意外重置状态栏高级配置

位置：  
[SettingsPage.vue](</C:/work/PG Butler/PGB1/src/views/SettingsPage.vue:30>)、[SettingsPage.vue](</C:/work/PG Butler/PGB1/src/views/SettingsPage.vue:247>)、[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:8>)、[StatusBar.vue](</C:/work/PG Butler/PGB1/src/components/StatusBar.vue:43>)

问题：  
`SettingsPage.vue` 自己维护了一个阉割版 `statusBarConfig`，只包含 `showTime/showDate/showWorked/showCountdown` 四个字段；但在保存考勤设置时，又会把这份对象直接整包写回 `status_bar_config`。  
而真正的状态栏配置在 `useStatusBar.ts` 中已经扩展到 `showPomodoro/pomodoroWork/pomodoroBreak/calendarRegion` 等字段，`StatusBar.vue` 也在真实使用这些字段。

影响：  
用户只要保存一次考勤设置，就会把番茄钟开关、番茄钟时长、节假日地区等配置静默覆写回默认值。这个问题不是“配置项缺失”，而是“无关页面写坏别的模块配置”，属于状态污染。

建议：  
`SettingsPage.vue` 不应再直接写 `status_bar_config`。若确实要写，至少应先读取完整对象再做 merge，不能用当前这份 4 字段对象整包覆盖。

### P1-02 HomePage 存在全局事件监听泄漏

位置：  
[HomePage.vue](</C:/work/PG Butler/PGB1/src/views/HomePage.vue:229>)

问题：  
主页在 `onMounted` 里注册了三个 Tauri 全局事件监听：

- `overtime-started`
- `overtime-ended`
- `clock-progress`

但只保存并释放了 `overtime-started` 的 `unlisten`。后两个监听没有保存释放句柄，页面每进出一次都会额外叠加一次监听。

影响：  
主页来回切换几次后，同一个事件会被重复消费。直接后果包括：

- `endOvertime()` 被重复触发
- `clock-progress` 逻辑重复执行
- 状态栏/主页快捷区的加班状态越来越不稳定

这是典型的“第一次没问题，越跑越怪”的状态型 bug。

建议：  
把三个 `listen(...)` 的返回值都收集起来，在 `onUnmounted` 中统一释放。

### P2-03 状态栏定时器的首轮 `setTimeout` 没有被跟踪和清理

位置：  
[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:67>)、[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:232>)、[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:266>)

问题：  
`startTimer()` 会先打一段对齐到整分钟的 `setTimeout(...)`，然后再开启 `setInterval(...)`。  
但当前代码只保存了 `setInterval` 的句柄，没有保存 `setTimeout` 的句柄，`stopTimer()` 也无法取消这个待执行的 timeout。

影响：  
如果该 composable 在首个整分钟到来前经历卸载/重挂载，旧 timeout 仍会触发，并可能再拉起一个新的 interval。之后 `stopTimer()` 只能清掉最后一个 interval，前面泄漏的 interval 会继续跑。

这个问题当前不一定高频触发，但它会把模块级单例做成“表面单例、实则可重入”的状态源，后期很难排查。

建议：  
把 timeout 句柄与 interval 句柄一起管理，`stopTimer()` 同时清理两者；timeout 回调内部也要再次确认当前是否仍需启动 interval。

### P2-04 截止日期排序使用 `new Date('YYYY-MM-DD')`，存在时区错位风险

位置：  
[HomePage.vue](</C:/work/PG Butler/PGB1/src/views/HomePage.vue:78>)、[HomePage.vue](</C:/work/PG Butler/PGB1/src/views/HomePage.vue:100>)

问题：  
主页的 `parseDeadline()` 直接调用 `new Date(deadline)` 解析纯日期字符串。  
在 JS 里，`'2026-04-14'` 这种格式会按 UTC 解析，而后续比较使用的是本地时区的 `today`。

影响：  
在 UTC 负时区，这个日期会被解释成“前一天傍晚”的本地时间。例如在 UTC-7，`2026-04-14` 会落到本地 `2026-04-13 17:00`。  
这会导致：

- 是否逾期判断提前一天
- `deadline` 排序顺序错误
- 同一份数据在不同地区机器上排序结果不一致

建议：  
不要用 `new Date('YYYY-MM-DD')` 解析业务日期。应拆成年/月/日后用本地构造函数创建日期对象，或者统一走本地日期工具函数。

### P2-05 序列帧重命名会吞掉帧文件级错误，可能产生“半成功”结果

位置：  
[files.rs](</C:/work/PG Butler/PGB1/src-tauri/src/commands/files.rs:77>)

问题：  
`rename_material()` 在处理 sequence 时，会先遍历目录内帧文件逐个重命名；其中帧文件 rename 使用了：

`let _ = fs::rename(...)`

也就是显式忽略错误。随后外层目录 rename 仍继续执行，并且整个命令仍可能返回成功。

影响：  
只要有任意一帧因为占用、权限、重名等原因改名失败，就可能出现：

- 目录名已经改了
- 一部分帧名改了
- 另一部分帧名没改
- 前端收到“成功”，但磁盘状态已不一致

这是典型的数据完整性问题，比单纯报错更危险。

建议：  
帧文件 rename 不应吞错。至少要在首个失败时中断并返回错误；更稳妥的方案是先预检冲突，再执行重命名。

### P2-06 项目里仍存在成片静默失败，违反当前协作红线

位置示例：  
[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:54>)、[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:71>)、[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:86>)、[useStatusBar.ts](</C:/work/PG Butler/PGB1/src/composables/useStatusBar.ts:122>)、[MaterialsPage.vue](</C:/work/PG Butler/PGB1/src/views/MaterialsPage.vue:162>)、[MaterialsPage.vue](</C:/work/PG Butler/PGB1/src/views/MaterialsPage.vue:245>)

问题：  
项目规范明确禁止“try-catch 后静默失败”，但当前仍有较多 `catch {}` / `catch { /* 忽略 */ }`：

- 状态栏配置读取失败
- 考勤记录读取失败
- 节假日 API 失败
- 项目素材扫描失败
- 笔记加载失败

影响：  
这些错误不会直接把页面打崩，但会把真实故障变成“UI 没更新”“某些标签消失”“偶发空白数据”，后续定位成本极高。  
尤其是本项目已经进入后期，越到后面越不该靠静默失败掩盖状态异常。

建议：  
至少补 `console.warn/error`；对用户可感知的功能，建议加非阻断提示或状态标记。

### P3-07 设计系统 SSOT 被多处硬编码绕开

位置示例：  
[FileDetailSidebar.vue](</C:/work/PG Butler/PGB1/src/components/FileDetailSidebar.vue:558>)、[StatusBar.vue](</C:/work/PG Butler/PGB1/src/components/StatusBar.vue:392>)、[PinboardPage.vue](</C:/work/PG Butler/PGB1/src/views/PinboardPage.vue:98>)

问题：  
当前仍有大量颜色、阴影、透明度、调色板直接写死在组件里，而不是通过 design token / 语义变量统一管理。

代表性例子：

- `FileDetailSidebar.vue` 直接写 `rgba(255,255,255,0.2)`、`rgba(0,0,0,0.45)`、`rgba(0,0,0,0.65)`
- `StatusBar.vue` 直接写 `background: #ffffff`
- `PinboardPage.vue` 直接写整组 `COLORS = ['#FF3B30', ...]`

影响：  
这类代码短期可用，但会持续侵蚀当前项目最重要的 SSOT 约束：

- 主题联动会越来越难
- 局部调色无法全局回收
- 明暗主题和视觉统一性会慢慢漂移

说明：  
像 Photoshop/PDF 品牌图标色这类“内容自身语义色”可以保留，但也应收敛到具名常量，不应继续散落。

建议：  
将生产 UI 中的硬编码值回收到 `design-system.css` 或专用主题配置；业务调色板则放入命名常量文件。

## 4. 系统性观察

### 4.1 现在的主要风险不是“编不过”，而是“状态被别的页面偷偷写坏”

本轮最值得重视的不是单个 API 调用失败，而是几个跨页面共享状态已经开始互相污染：

- `SettingsPage` 覆写 `useStatusBar` 配置
- `HomePage` 全局监听累积
- `useStatusBar` 的单例定时器管理不完整

这三个问题是同一类风险：共享状态源缺少边界保护。

### 4.2 项目后期更需要“显性失败”，而不是“安静失败”

当前项目体量已经接近收尾，真正危险的是“有问题但看起来像没问题”。  
静默失败会让 QA 和使用者只能观察到结果异常，却没有任何定位线索。

### 4.3 文档入口必须恢复可信度

你要求每次都从 `INDEX.md` 进入是对的，但前提是它必须准确。  
现在 `INDEX.md` / `README.md` 的版本口径已经落后于真实代码，继续放任会让后续所有审查都先踩一遍假信息。

### R-1 ｜ SettingsPage 保存考勤时覆写 useStatusBar 完整配置

**来源**：GPT-5 Codex 首发（P1-01）· Claude 实地验证属实
**文件**：
- `src/views/SettingsPage.vue:28-36`（`statusBarConfig` 阉割版定义）
- `src/views/SettingsPage.vue:247-248`（保存时整包覆盖）
- `src/composables/useStatusBar.ts:8-17`（真实完整类型定义）
- `src/components/StatusBar.vue`（消费番茄钟/节假日字段）

**根因**（已验证）：

`SettingsPage.vue` 自己定义了一个 4 字段的阉割版 `statusBarConfig`：
```ts
const statusBarConfig = ref<{ showTime, showDate, showWorked, showCountdown }>
```

而 `useStatusBar.ts` 中的 `StatusBarConfig` 实际有 **8 个字段**：
```ts
{ showTime, showDate, showWorked, showCountdown,
  showPomodoro, pomodoroWork, pomodoroBreak, calendarRegion }
```

保存考勤设置的 `handleAttendanceSave()` 在 L247 执行：
```ts
localStorage.setItem(STATUS_BAR_CONFIG_KEY, JSON.stringify(statusBarConfig.value))
reloadStatusBarConfig()
```

**整包写入 + 触发 reload**——用户配置的番茄钟开关、工作/休息时长、节假日日历地区**全部静默消失**。

**爆炸半径**：用户 A 下午打开番茄钟 + 切换日历到日本节假日，晚上保存一次考勤密码 → 番茄钟消失、节假日回到"auto"。无错误、无日志、无警告。属于"每次保存都会触发、用户无法自行定位"的**数据丢失级 bug**。

**为什么 Claude 首轮漏了**：审了 SettingsPage.vue 1-280 行，识别出"双数据源维护"（Y-02），但没继续追踪 `statusBarConfig.value` 在 save 时的整包写入，也没和 `useStatusBar.ts` 的完整类型定义做交叉比对。**这是三路交叉审查的直接价值证明**。

**修复方案**：
```ts
// Option A: 合并 merge，不覆盖未知字段
const existing = JSON.parse(localStorage.getItem(STATUS_BAR_CONFIG_KEY) ?? '{}')
localStorage.setItem(STATUS_BAR_CONFIG_KEY,
  JSON.stringify({ ...existing, ...statusBarConfig.value }))

// Option B（推荐）: 彻底解耦 — 移除 SettingsPage 里的 statusBarConfig 副本，
// 状态栏配置只通过 StatusBar 组件的长按配置面板修改，不让 SettingsPage 染指
```

### R-2 ｜ `launch_shortcut` 命令注入漏洞

**来源**：Claude 独门
**文件**：`src-tauri/src/commands/shortcuts.rs:80-84`

```rust
"web" => {
    std::process::Command::new("cmd")
        .args(["/C", "start", "", &path])
        .spawn()
```

**问题**：`cmd /C start "" <path>` 把 path 交给 cmd 解析。path 若含 `&` / `|` / `>` / `<` / `^` / `%`，cmd 会解释为命令分隔符或变量。

**攻击场景**：用户添加 URL `https://x.com & calc.exe` → 点击启动计算器。威胁等级中（本地工具），但**可编程触发任意命令执行**，shortcuts.json 被污染或用户误输入即触发。

**修复**：项目已注册 `tauri_plugin_opener::init()`（`lib.rs:25`），直接复用：
```rust
"web" => {
    tauri_plugin_opener::open_url(&path, None::<&str>)
        .map_err(|e| format!("打开网页失败: {}", e))?;
}
```

### R-8 ｜ `HomePage.vue` 全局事件监听泄漏

**来源**：GPT-5 Codex 首发（P1-02）· Claude 实地验证属实
**文件**：`src/views/HomePage.vue:244-257`

已验证的实际代码：
```ts
let unlistenOvertime: UnlistenFn | null = null   // L229 只保存一个

onMounted(async () => {
  // ...
  unlistenOvertime = await listen('overtime-started', () => { startOvertime() })  // L244 ✅ 保存

  listen('overtime-ended', () => { endOvertime() })                              // L248 ❌ 裸调用
  listen('clock-progress', (event: any) => {                                     // L252 ❌ 裸调用
    const step = event.payload?.step
    if (isOvertime.value && (step === 'success' || step === 'already-done')) {
      endOvertime()
    }
  })
})

onUnmounted(() => {
  // ...
  if (unlistenOvertime) unlistenOvertime()   // L261 只释放一个
})
```

**爆炸半径**：主页来回切换 N 次 → `overtime-ended` / `clock-progress` 被消费 N 次。直接后果：
- `endOvertime()` 重复触发，状态栏加班标签闪烁
- 退勤后的状态清除被叠加执行
- 典型的"第一次好的，越用越怪"状态 bug

**为什么 Claude 首轮漏了**：只做了"文件级 listen/unlisten 配对"的 grep 扫描，9 个文件都有 `onUnmounted`，于是判定"基本配对完整"。**没有下钻到 HomePage.vue 的函数级别**逐一对配。

**修复**：
```ts
let unlistenOvertimeStarted: UnlistenFn | null = null
let unlistenOvertimeEnded: UnlistenFn | null = null
let unlistenClockProgress: UnlistenFn | null = null

onMounted(async () => {
  unlistenOvertimeStarted = await listen('overtime-started', () => startOvertime())
  unlistenOvertimeEnded = await listen('overtime-ended', () => endOvertime())
  unlistenClockProgress = await listen('clock-progress', (event: any) => { /* ... */ })
})

onUnmounted(() => {
  unlistenOvertimeStarted?.()
  unlistenOvertimeEnded?.()
  unlistenClockProgress?.()
})
```

### R-9 ｜ `rename_material` 帧文件半成功风险（数据完整性）

**来源**：GPT-5 Codex 首发（P2-05）· Claude 验证属实
**文件**：`src-tauri/src/commands/files.rs:88-95`

已验证的实际代码：
```rust
if is_frame {
    let fsuffix = &fname[base_name.len()..];
    let new_fname = format!("{}{}", new_base_name, fsuffix);
    let _ = fs::rename(&fpath, fpath.parent().expect("...").join(&new_fname));  // L91 ⚠️ 显式吞错
}
// ...
fs::rename(&path, &new_path).map_err(|e| format!("重命名目录 {} 失败: {}", ...))?;  // L95 外层目录继续
```

**爆炸半径**：只要有任意帧（文件占用/权限/重名）rename 失败，则：
- 外层目录名已改
- 部分帧名已改
- 部分帧名未改
- 整个命令**仍然返回 `Ok(())`**，前端收到成功

结果是磁盘状态不一致，用户无从察觉，直到打开播放序列帧时看到"部分帧缺失"。

**修复**：
```rust
for frame_entry in frames.flatten() {
    // ... 提取 fname / fstem / new_fname ...
    if is_frame {
        fs::rename(&fpath, new_frame_path)
            .map_err(|e| format!("帧文件重命名失败 {}: {}", fname, e))?;  // 传播错误
    }
}
// 更稳妥：先预检所有目标名冲突，确认无冲突后再批量执行
```

### Y-3 ｜ `useStatusBar` setTimeout 未跟踪 + 单例可重入

**来源**：GPT-5 Codex 首发（P2-03）
**文件**：`src/composables/useStatusBar.ts:67, 232-239, 266-269`

```ts
function startTimer() {
  if (timer) return
  const msToNextMinute = (60 - now.value.getSeconds()) * 1000 - now.value.getMilliseconds()
  setTimeout(() => {                           // ❌ 句柄未保存
    tick()
    timer = setInterval(tick, 60_000)
  }, msToNextMinute)
}

function stopTimer() {
  if (timer) { clearInterval(timer); timer = null }
  // ❌ 无法清理前面 setTimeout 的待执行回调
}
```

**爆炸半径**：组件在首个整分钟前卸载/重挂载 → 旧 timeout 仍触发 → 再拉起一个新的 interval → `stopTimer()` 只清最后一个。**表面单例，实则可重入**。

**修复**：
```ts
let pendingTimeout: ReturnType<typeof setTimeout> | null = null

function startTimer() {
  if (timer || pendingTimeout) return
  // ...
  pendingTimeout = setTimeout(() => {
    pendingTimeout = null
    tick()
    timer = setInterval(tick, 60_000)
  }, msToNextMinute)
}

function stopTimer() {
  if (pendingTimeout) { clearTimeout(pendingTimeout); pendingTimeout = null }
  if (timer) { clearInterval(timer); timer = null }
}
```

### Y-4 ｜ `new Date('YYYY-MM-DD')` 时区错位

**来源**：GPT-5 Codex 首发（P2-04）· Claude 实地验证属实
**文件**：`src/views/HomePage.vue:81-85`

```ts
function parseDeadline(deadline: string | null | undefined): Date | null {
  if (!deadline || !DATE_PATTERN.test(deadline)) return null
  const d = new Date(deadline)    // ❌ '2026-04-14' 按 UTC 解析
  return isNaN(d.getTime()) ? null : d
}
```

**JS 规范**：`new Date('YYYY-MM-DD')`（纯日期格式）按 UTC 00:00 解析，而后续排序用的 `today = new Date(); today.setHours(0,0,0,0)` 是**本地时区**。

**爆炸半径**：
- UTC-7（美西）机器上，`'2026-04-14'` 被解释为 `2026-04-13 17:00` 本地
- 是否逾期判断提前一天
- 同一数据在不同时区机器排序结果不同

**威胁等级**：开发团队在中国（UTC+8）时看不到，但海外用户或 CI 机器会触发。

**修复**：
```ts
function parseDeadline(deadline: string | null | undefined): Date | null {
  if (!deadline || !DATE_PATTERN.test(deadline)) return null
  const [y, m, d] = deadline.split('-').map(Number)
  return new Date(y, m - 1, d)   // ✅ 本地时区构造
}
```

## 9. 结语

**三个 agent 做独立审查、再做交叉整合**这个工作流证明了价值：
- 任何单一 agent 都有 20%~30% 的盲区
- 不同 agent 擅长的维度不同（Claude 细颗粒 + 安全；GPT 状态 bug + 编译验证；Gemini 架构视角 + 正面评价）
- 交叉整合后的报告覆盖度显著高于任一单份

**对项目本身的结论**：

PGB1 是一个**具备发布水准的专业工具**——
- 架构分层清晰，Rust panic 安全几乎完美
- 大部分设计模式都有**值得借鉴的闪光点**（DirSnapshot / PSD 并发去重 / 墙钟分段 sleep / serde 防御）
- 真实编译/构建链完全干净（GPT 已验证）

**但已进入"结构性细节开始反噬"的阶段**——
- 一个 `statusBarConfig` 阉割副本导致数据丢失（R-1）
- 一个 `let _ = fs::rename` 导致帧文件半成功（R-9）
- 一个 `new Date('2026-04-14')` 导致海外时区排序错乱（Y-4）
- 一个 `--color-success-500` 笔误导致品牌色断层（R-5）

这些问题都不是"代码能力差"，而是"项目后期纪律性微衰减"的产物。按本报告 Sprint 1~3 的顺序推进，4 周内可以回到健康水位。

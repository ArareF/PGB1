# PG Butler (PGB1) 项目代码审查与优化报告 - Gemini版

## 1. 概述与结论

基于项目协作契约与系统防熵增的约束，本次代码审查覆盖了系统核心的前端全局架构、UI 页面级大组件、响应式状态管理（Composables），以及负责 I/O 与耗时计算的 Rust 后端模块。
**整体评价**：
项目基本遵循了“Single Source of Truth(SSOT)”思想，核心颜色尺寸通过 `DesignSystem.css` 进行管控。
逻辑与视图的分层结构初步建立，但在“超大型组件管理”和“状态复用耦合度”上，存在较高隐患，特别是 `TaskPage.vue` 承担了过多的领域职责。后端部分对于并发与缓存做了巧妙封装，但部分大型文件职责过重。

## 2. 前端架构与组件（UI / Vue端）

### 2.1 巨型页面组件过载
**目标文件**：`src/views/TaskPage.vue` (~ 800行以上), `src/views/SettingsPage.vue` (~ 800行以上)
*   **诊断**：
    *   `TaskPage.vue` 是一个典型的“上帝组件（God Component）”。它既处理 Tree/Name 两种视图模式，又管理拖拽上传逻辑、版本缓存、PSD并发缩略图触发，还杂糅了大量的 `div` 布局逻辑。一旦扩展新的视图或交互方式，“爆炸半径”将非常大。
    *   `SettingsPage.vue` 将所有配置（工作流、翻译、考勤、通用设定）塞进了一个单文件。其 `v-model` 直接绑定在单个庞大的配置对象或者独立 ref 上，不利于局部重渲与维护。
*   **优化建议（Trade-off）**：
    *   **方案A（最小变动提取组件）**：将 `SettingsPage` 的各 Tab 抽出独立子组件（如 `WorkflowSettings.vue`, `TranslationSettings.vue`），在父级通过 `<component :is="activeTab" />` 挂载。优点是改动极小，缺点是没有触及 `TaskPage` 的痛点。
    *   **方案B（深层拆解分离业务 Hooks与UI）**：对于 `TaskPage.vue`，应将非视图相关的业务流抽出（例如 `useMaterialUploader()` 或 `useTaskContext()`）。将列表渲染区域抽出为 `<TaskListView />` 等子组件。优点是彻底解耦、低熵，缺点是涉及全局状态重构，需较高的时间成本。
    *   **推荐**：**方案B**（分批次重构）。建议优先拆分 `SettingsPage.vue` 作为练手，然后重点攻坚 `TaskPage.vue` 的交互层和视图层分离。

### 2.2 Composables 的边界与全局单例问题
**目标文件**：`src/composables/useStatusBar.ts`, `src/composables/usePsdThumbnail.ts`, `src/composables/usePinboard.ts`
*   **诊断**：
    *   `useStatusBar.ts` 业务逻辑充实，使用了大量模块级闭包变量（如 `const config = ref(...)`, `const now = ref(...)`），其本质是一个伪 Store，它成功复用了全局状态，设计合理。但在处理 IP 缓存、节假日探测以及番茄钟定时器时，存在部分强耦合，文件较长（近 500 行）。
    *   `usePsdThumbnail.ts` 基于 JS 字典做缓存拦截以防止同一时刻重复发送 IPC 到 rust。其并发控制 `pending` 的 map 实现非常优雅，完全符合短中期预防重复解析的需求。
*   **优化建议**：
    *   `useStatusBar.ts` 中的国家节日/考勤API抓取逻辑可以转移至专门的纯函数文件中进行治理（如 `utils/holiday.ts`），从而保证 Composable 只作为前端数据与视图响应的黏合剂，让代码更加遵循单一职责原则。

### 2.3 FileDetailSidebar.vue 的渲染性能安全
**目标文件**：`src/components/FileDetailSidebar.vue`
*   **诊断**：大量依赖 `v-if` 与 `v-else-if` 来进行多种格式（MP4、PSD、PDF、TXT、Image）的按需加载。这种设计相对合理地避免了无用组件挂载，防备了资源过载。
*   **关注点**：在 PSD 与 PDF 共存加载并快速切换侧边栏状态时，需确认在 `watch` 监听器变更期间是否严格取消了之前的异步进程（比如读取巨型 PDF）。建议补充一个 AbortController 的取消令牌机制，增强“防御性编程”。

## 3. 后端逻辑分析（Rust 端）

### 3.1 扫描流程的复杂大一统（scanning.rs）
**目标文件**：`src/commands/scanning.rs` (超 1600 行)
*   **诊断**：文件通过预取快照 `DirSnapshot` （目录内存缓存）极大提升了并发扫描进度和大小的计算效率，这是设计上的闪光点。然而整个文件将项目解析（ProjectInfo）、任务解析（TaskInfo）、素材列表获取（MaterialInfo）、原型子菜单处理（Prototype），全部揉在一个文件里。
*   **优化建议**：将纯实体结构和快照结构 (`DirSnapshot`) 拆分到专门的 `scanner_core` 或 `snapshot.rs` 中，使 API 命令注册点 (`scan_projects`, `scan_tasks`) 与核心底层探测剥离。

### 3.2 翻译及 PDF 渲染耦合（translation.rs）
**目标文件**：`src/commands/translation.rs` （超 1100 行）
*   **诊断**：此文件集成了向 Gemini 调用 SSE 的流处理，PDF 的分页与排版解析，甚至还涉及非常底层的 TTF 字体解析与 Identity-H 字符编码与 PDF 格式内部构建（`add_yahe_font`, `extract_single_ttf_from_data`）。把 PDF 内部对象操控的逻辑放在 `translation.rs` 内严重超出了命名职责边界。
*   **优化建议（强烈推荐执行）**：
    需要将所有 PDF 字体相关的底层工具剥离到 `utils/pdf_font_utils.rs` 中。`translation.rs` 仅应该保留处理文本进出的 Command 函数。不仅代码结构更低熵，对于后续寻找错误或升级处理引擎也能提高可维护性。

## 4. 关键原则（SSOT & Simplicity）检查结果
1.  **硬编码检测**：检查发现核心界面的主题色彩并未硬编码配置，基本能正常回落到 DesignSystem Token。极少部分组件可能有零散行内布局，影响甚微。
2.  **静默失败与日志打点**：Rust 端虽然很多 `Err` 返回了字符串，但在部分复杂 `unwrap_or` 或者 `catch` 中，缺乏关键日志抛出至前端终端供调试使用。这在未来遇到死锁或路径缺失时可能是排障痛点。
3.  **代码卫生与遗留历史**：未见明显的 "Orphans"（如废弃的旧版本未移除）代码片段，体现了较好的模块更迭记录。
